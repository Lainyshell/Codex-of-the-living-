# Governance Charter
## Codex of the Living — Verdigris Botanica Tribal Nation

**Version:** 1.0
**Effective Date:** 2026-08-06
**Governing Authority:** Verdigris Botanica Tribal Nation

---

## 1. Purpose

This charter defines who has authority over the Codex of the Living infrastructure system, how authority is transferred, how decisions are made, and how powers are limited. It is designed to ensure the system outlives any single individual and remains under the lawful control of the Verdigris Botanica Tribal Nation (VBTN).

---

## 2. Governance Roles

### 2.1 System Steward

The **System Steward** is the primary technical and operational authority for the system.

**Responsibilities:**
- Day-to-day operational decisions
- Approving routine code changes and deployments
- Maintaining documentation and runbooks
- Coordinating with vendors and cloud providers
- Escalating critical decisions to the Elder Council

**Current Steward:** Alaina Padgett (`@Lainyshell`)
**Appointment:** By Tribal Resolution

**Powers limited by:**
- Cannot unilaterally approve Critical Changes (see Section 4)
- Cannot transfer, sell, or assign system assets without Elder Council approval and a Tribal Resolution
- Cannot remove other stewards from their roles

---

### 2.2 Tribal Technical Lead

The **Tribal Technical Lead** is the backup operational authority and primary technical successor.

**Responsibilities:**
- Understand full system architecture and operations
- Serve as primary approver on Critical Changes alongside the System Steward
- Assume System Steward duties if the Steward is unavailable
- Maintain technical competency of the stewardship circle

**Appointment:** By System Steward with Elder Council confirmation

### 2.3 Elder Council Seat

The **Elder Council Seat** is a non-technical governance authority representing the Nation's interests and values.

**Responsibilities:**
- Co-approve all Critical Changes affecting tribal law references, data sovereignty, or jurisdictional settings
- Co-approve succession transitions
- Hold veto authority over any decision that conflicts with tribal governance instruments
- Receive and review all abuse alerts generated by system safeguards

**Appointment:** By VBTN Elder Council designation

### 2.4 Stewardship Circle

The **Stewardship Circle** consists of 3–5 trusted family members and Nation members who:

- Understand what the system does and what it must never do
- Can recognize and report misuse
- Receive training per [`docs/STEWARD_TRAINING_GUIDE.md`](STEWARD_TRAINING_GUIDE.md)

## 3. Decision-Making Authority

### 3.1 Routine Decisions
Made by the **System Steward** alone:
- Bug fixes and minor code changes
- Documentation updates
- Non-critical dependency updates
- Operational configuration changes within established parameters

### 3.2 Standard Decisions
Require approval by **System Steward + Tribal Technical Lead**:
- New feature deployments
- Vendor onboarding (non-critical)
- Schema changes that are additive only
- Security patches

### 3.3 Critical Decisions
Require approval by **System Steward + Tribal Technical Lead + Elder Council Seat** plus a documented Tribal Resolution:
- See Section 4 for the full Critical Change list

---

## 4. Critical Change Protocol

The following changes are **Critical Changes** and require multi-steward approval plus a Tribal Resolution:

| Change Type | Why Critical |
|---|---|
| Database schema changes (destructive) | May permanently alter or destroy tribal records |
| Authentication / IAM configuration | Controls who has access to all data |
| Jurisdiction or governance document changes | Alters legal foundation of the system |
| Vendor or cloud platform changes | Affects data sovereignty and continuity |
| Integration additions or removals | Affects data flow and third-party exposure |
| System shutdown or decommissioning | Irreversible; affects Nation's operations |
| Export of bulk member or financial data | High misuse risk |
| Changes to `app/config.py` TRIBAL_GOVERNANCE block | Core governance references |
| Changes to `CODEOWNERS` | Controls review authority |

See [`docs/CRITICAL_CHANGE_PROTOCOL.md`](CRITICAL_CHANGE_PROTOCOL.md) for the full workflow.

## 5. Succession

### 5.1 Temporary Absence
If the System Steward is temporarily unavailable:
- The **Tribal Technical Lead** assumes operational authority
- Routine decisions proceed normally
- Critical decisions are held until the Steward returns unless the absence exceeds 30 days

### 5.2 Extended Absence (30+ days)
If the System Steward is unavailable for 30+ days:
- The Tribal Technical Lead assumes full System Steward authority
- The Elder Council Seat is notified
- The Stewardship Circle is convened to discuss succession

### 5.3 Permanent Incapacity or Death
If the System Steward permanently cannot serve:
1. The **Tribal Technical Lead** immediately assumes System Steward authority
2. The **Elder Council Seat** convenes the Stewardship Circle within 14 days
3. A new System Steward is nominated by the Stewardship Circle and confirmed by Tribal Resolution within 60 days
4. All credentials and access are audited and rotated within 7 days of succession

### 5.4 No Designated Successor
If no Tribal Technical Lead has been designated and the System Steward cannot serve:
1. Elder Council Seat has emergency authority to engage a trusted technical steward
2. That steward operates with Elder Council oversight only
3. A formal designation process must begin within 30 days

---

## 6. Power Limitations

No single individual may:
- Approve a Critical Change without co-approval from at least one other designated steward
- Transfer, sell, or assign system assets unilaterally
- Remove another steward's access without Elder Council approval
- Disable the safeguards module (`app/safeguards.py`) without multi-steward approval
- Change the CODEOWNERS file without multi-steward approval

---

## 7. Charter Amendments

Amendments to this charter require:
1. A written proposal circulated to all three governance roles
2. A 14-day comment period
3. A Tribal Resolution adopting the amendment
4. A pull request in the repository approved by all three governance roles (or available successors)
